# nx5：64K 固定配置与验收

已将这轮推荐参数固定为 **65536 上下文容量、window176、bank64、DSpark draft7、CUDA 映射专家缓存**。
64K 容量分配及实际 8218-token 输入的六字段检索均通过，没有新增 OOM kill。
验收范围是用户选定的“容量 + 实际约 8K 长输入”，**尚未测试填满 64K 历史**。

配置文件：[minicpm-v47-64k.json](../configs/minicpm-v47-64k.json)。
固定入口：[run-64k.py](../scripts/minicpm/run-64k.py)。
原始运行记录：[reports/2026-10-21-nx5-64k-final](../reports/2026-10-21-nx5-64k-final/)。

## 为什么窗口从 200 调整为 176

启动日志实测：64K 主模型 KV 占 680 MiB，五层草稿模型的 f16 KV 占 640 MiB，合计 1320 MiB。
不能只计算主模型的 KV。相较 8K，二者合计增加约 1155 MiB。

窗口由 200 减到 176，可释放 `24 × 40 × 1.2890625 = 1237.5 MiB` 的专家缓冲，
基本抵消这部分增长。主模型在 draft7 下还分配了约 502.5 MiB recurrent state，
这些状态、运行缓冲和操作系统也占用同一块物理内存。

## 实测结果

| 测试 | 实际输入 / 输出 token | prefill | decode token/s | 进程总耗时 | 最低可用内存 |
|---|---:|---:|---:|---:|---:|
| 64K 容量、英文 SVG 短测 | 108 / 1024 | 5.03 秒 | **17.16** | 74.16 秒 | 1219 MiB |
| 64K 容量、约 8K 记录检索 | **8218 / 108** | **212.70 秒** | **14.22** | 232.00 秒 | **1130 MiB** |
| 固定入口、中文鹈鹕原题 | 38 / 2315 | 2.75 秒 | **15.54** | **161.34 秒** | 1222 MiB |

容量短测采用贪心采样以对照前轮基准；长输入采用最终固定的 instruct 采样。
这两种任务的输出长度、输入长度和采样不同，不能将其速率差异全部归因于上下文。
所有停顿均计入耗时。长输入的 108-token 回答较短，14.22 不是长时间稳定吞吐保证。

长输入由 [make-context-probe.py](../scripts/minicpm/make-context-probe.py) 生成，使用当前模型的 tokenizer
选取至少 8192 token 的正文，实际为 8207 token；加聊天模板后引擎报告 8218。
共 227 条虚构仓库记录，在约 3%、20%、40%、60%、80%、97% 位置选取六个随机核验码，
问题置于全部记录之后。六项均原样返回，JSON 可解析，无多余字段。
[验收记录](../reports/2026-10-21-nx5-64k-final/long-input-assessment.json) 保存了预期、实际值和指标。
这验证了本次输入未被缩成短提示词并且模型能完成这组检索；不是全面长上下文质量评测。

最后通过 `run-64k.py` 实际运行了完整中文原题，正常自然结束，总耗时约 **2 分 41 秒**。
[原始 HTML](../reports/2026-10-21-nx5-64k-final/pelican-fixed/pelican.html) 与前轮 8K/GPU/draft7
结果逐字节一致，SHA256 为 `9e6b5a65bc40a515efe718d13c699043f2568a5cc575e72d80b128b700ecfc0a`。
因此这次扩容没有改变该样本的 HTML 内容，原有车轮定位错误也原样保留。
所有任务结束后无残留 `llama-cli` 进程，`oom_kill` 仍为 26，没有增加。

## 鹈鹕为什么变差：补充对照

较早的 CPU/instruct 输出给前后轮分别设置了明确旋转中心；GPU/draft7 输出改成了
`transform-origin:center`，缺少正确参考盒或单独轮心，导致整个车轮绕 SVG 视口旋转。
画面差异来自模型生成的 HTML 不同，浏览器没有把同一份 HTML 随机渲染坏。

新增对照保持 8K/window200、GPU 映射、中文原题、官方模板、seed42 和 instruct 参数，
仅关闭 DSpark。结果是 2316 token、14.22 token/s；浏览器运行后，车轮同样离开车架。
[未经编辑的 HTML](../reports/2026-10-21-nx5-64k-final/quality-d0/pelican.html) 与
[700ms 截图](../reports/2026-10-21-nx5-64k-final/quality-d0/frame-700.png) 已保留。

因此，**关闭投机不能消除本次 SVG 定位错误，不能将其单独归咎于 DSpark**。
两轮模板 SHA256 相同，未降低权重量化精度；38-token 输入加约 2300-token 输出也没有超过 8K 容量。
CPU/GPU 计算和不同验证批次可能改变生成分支，但没有固定前缀的逐步 logits 对照，
不能把全部差异确定归因于浮点误差，也不能宣称端到端质量完全等价。

此前映射内存与普通 CUDA buffer 的专家算子数值测试、512-token 全模型输出对照仍然有效，
但它们的覆盖范围不等于全部绘图能力评测。固定的是运行参数，**鹈鹕视觉任务仍不算通过**。

## 运行与版本固定

在 nx5 上执行：

```bash
cd /home/nx/github/qwen38-kvmem/minicpm-audit-20261021
python3 scripts/minicpm/run-64k.py samples/pelican-user-prompt-20261021.txt
```

可以换成任意 UTF-8 提示词文件。默认结果在 `logs/64k/`：`.out` 为原始输出，
`.json` 记录完整命令、环境和性能，`.memory.jsonl` 保存内存与回收计数采样。
`--tag`、`--output` 调整归档位置，`--tokens`、`--seed` 显式调整输出预算和种子。
示例中的默认 6144-token 输出预算应从总上下文容量中预留。

入口读取固定 JSON，并校验本轮 `libllama.so.0`、`libggml-cuda.so.0` 和聊天模板的 SHA256。
库或模板发生变化时会拒绝启动，避免误用另一版本冒充当前配置。
引擎是原有 `a64932e` 构建加本轮隔离补丁库；没有覆盖原始生产库。
重新构建或升级后需重新验收并更新配置中的哈希。
已执行的配置 SHA256 为 `bec2c47c32fe6979db398169baf4326cda849a1ad8da25bec0a1e1728251f59b`，
[归档副本](../reports/2026-10-21-nx5-64k-final/fixed-profile.json) 与 nx5 正在使用的文件一致。

该入口是单请求 CLI。HTTP 服务、无限多轮常驻内存以及实际填满 64K 后的速度尚未验收。
旧 `run-fast-8k.py` 保留为 8K 历史对照；旧 `start.sh`/`env.sh` 的历史 preset 不代表当前固定配置。
